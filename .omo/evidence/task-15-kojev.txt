All three question types return their correct typed field (noul / choice /
score), probabilities are normalised, and usage is reported.

These values are checkpoint-specific rather than uniform, which matters: before
the serve.py fix landed earlier this session, this same request would have
returned well-formed numbers from a RANDOMLY INITIALISED head, and this QA would
have "passed" while serving a model that had never been trained.

## Malformed input: every case 422 with the typed envelope

    missing type                     HTTP 422  error_type=validation_error
    options AND criteria             HTTP 422  error_type=validation_error (question_options)
    neither options nor criteria     HTTP 422  error_type=validation_error (question_options)
    300 options                      HTTP 422  error_type=schema_error (choice question limit)
    empty questions                  HTTP 422  error_type=validation_error (too_short)

The 300-option rejection the plan names explicitly is enforced at the schema
boundary and surfaces as schema_error rather than a generic validation failure.

## Wire contract note

The request shape is {"model": str, "state": str, "questions": {name: question}}.
`questions` is a KEYED MAPPING, not a list, and `model` is required. My first
payload used a list and was correctly rejected with 422; the contract was then
read from the source rather than guessed at.
