## Root cause

`/data2` is NFS with healthy sequential throughput but pathological small-file
metadata cost, measured on gpu01:

```text
/data2 sequential write     14.8 MB/s      (healthy)
/data2 small-file create    2.58 files/s   (100 files in 38,765 ms)
/dev/shm small-file create  3,571 files/s
ratio                       1,384x
/ (root)                    100% full, 890M free -> no local scratch
```

A Python environment is tens of thousands of small files, so any per-job
environment construction is fundamentally too slow here. The network was never
the problem: PyPI measured 41.6 MB/s.

## Corrections landed on feat/infra

1. Shared warm package cache. Both templates defaulted `UV_CACHE_DIR` to a
   per-job path and sbatch does not propagate the submitting shell's value, so
   every job re-downloaded multi-GB CUDA wheels. Now a shared
   `/data2/jeffrey/kojev/uv-cache`. Proven by job 13620:
   `Resolved 92 packages in 1ms` with ZERO Downloading lines.
2. `uv sync --no-dev`. basedpyright ships ~20k tiny typeshed stub files and
   pulls nodejs-wheel-binaries; the cluster trains, it does not lint.
   Downloads fell from 29 packages to 1.
3. `UV_LINK_MODE=hardlink`, replacing copy, so torch is not duplicated per job.
4. Prebuilt shared venv. Even hardlinking ~10k torch files exceeds the smoke
   wall clock, so jobs must not build environments at all. Templates prefer
   `/data2/jeffrey/kojev/venv-shared` and fall back to a per-job sync only when
   it is absent. Because jobs never write to it, the original 13597 `.venv`
   race cannot recur.
5. Direct interpreter launch. With the shared venv on PATH the job execs its own
   python rather than going through `uv run`, which would still resolve the
   project and consult the lockfile against a read-only environment.
6. `--` tolerance. The plan's documented command is
   `sbatch scripts/slurm/smoke.sbatch -- python -m kojev.train ...`; sbatch
   forwards that leading `--` as `$1`, so the templates now shift it off.
